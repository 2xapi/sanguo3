## 01　项目定案与使用方式

### 1.1 项目目标

将指定MD版本《三國志Ⅲ》重写为打开网址即可游玩的独立单机网页游戏。分开报告视觉、交互、数据、规则、声音与AI的完成情况。完整还原是逐项关闭差异的目标，不能由“看起来像”或“可以运行”推导出来。

经典游戏画布以内保持目标版本的布局与流程。网页全屏、备份、显示模式和按键设置放在画布之外。浏览器能力与游戏机制分层处理，不能用网页适配改写原版菜单或规则。

### 1.2 硬约束

- 不提供ROM上传、ROM加载、模拟器内核、补丁运行或MOD依赖。
- 不用其他平台、地区版本或其他三国游戏的经验替代本版本证据。
- 未确认的公式、角色数据、AI、字体和声音必须有明确状态；开发占位不得标成已还原。
- 游戏状态经统一命令入口修改，UI和AI不能绕过校验直接改资源。
- 先完成一个可核对场景，再复用已通过的组件扩展内容。
- 本地存档采用自定义格式，不宣称与卡带存档兼容。

### 1.3 决策和记录

由项目负责人维护范围与版本；资料负责人维护证据与冲突；开发者维护实现与验证；验收者核对可观察结果。一人承担多个角色时仍保留独立检查表。每项决定记录日期、依据、影响范围与替代方案。

变更目标语言、参考版本、显示模式或主验收场景时，创建基准新版本，并重新评估受影响任务；不静默覆盖旧资料。

## 02　还原范围与项目边界

### 2.1 分维度验收

| 维度 | 需要达到的行为 | 依据与边界 |
| --- | --- | --- |
| 画面 | 布局、字形、图块、颜色、帧序一致 | 同状态截图或指定帧；采集误差需说明 |
| 操作 | 菜单、焦点、取消、翻页、输入节奏一致 | 原版按键与逻辑动作记录 |
| 数据 | 剧本、人物、城市、关系逐字段相符 | 每个实体和字段可追溯 |
| 确定性规则 | 条件、消耗、取整、时序与结果相符 | 完整前提下可重复的案例 |
| 随机与AI | 达到明确声明的验证层次 | 自身可重复、分布相符、序列相符分别报告 |
| 声音 | 音色、曲目、触发、循环与混音相符 | 有时间标记的音频或录像 |
| 网页工程 | 构建、响应、存档、恢复、兼容可用 | 网页测试；不等于原版还原通过 |

### 2.2 最终范围

功能清单应覆盖目标版本的开局选项、剧本、城市场景、全部菜单、战略指令、战斗、事件、人物创建、存读档与结束条件。若目标版本支持本地多君主轮流操作，将其纳入清单；是否支持及具体行为先查证。

联网多人、账号、云存档、新剧本、新玩法、高清重绘和现代化游戏内菜单不属于默认范围，另立变更。扩展功能不能改变原版对照模式的基准。

### 2.3 分阶段范围冻结

首个场景只冻结到一个明确状态和一段完整菜单路径；首个规则闭环只冻结到一条已确认指令、一次已确认月份推进与一次存档恢复。战斗与全内容后续按清单扩展，不在首阶段提前承诺。

每个里程碑列出：包含项、排除项、依赖、演示入口、参考ID、通过条件及阻断项。阶段性缩小范围不能降低范围内的还原标准。

## 03　建立参考资料与证据库

### 3.1 版本锁定

项目目标名称已由用户指定，尚需确认实际语言画面、地区／修订标识及参考来源。版本结论分为“用户指定目标”“附件静态观察”“独立资料确认”“画面行为确认”，四者分别记录，不相互替代。

附件地区J、产品编号和日期作为线索保存；不据此断言附件是未修改的官方繁体中文版。标题、菜单、说明书及录像应核查是否属于同一版本。资料冲突时保留冲突记录，不选最方便实现的一份直接覆盖。

### 3.3 证据与实现分别标记

证据状态：未采集、已采集、待验证、已确认、存在冲突。实现状态：未开始、开发中、已实现、回归通过。对照状态：未对照、对照失败、局部通过、通过、阻断、不适用。三类状态分列，不能把“实现了”写成“已确认”。

每份参考记录referenceId、版本、来源、取得日期、作者或提供者、文件路径、SHA-256、原始尺寸／帧率、采集处理、可用范围和证据状态。每个规则案例还要记录初始条件、操作、结果、重复次数与不能控制的变量。

## 04　先完成一个标准城市场景

### 4.1 场景冻结单

填写：sceneId、目标版本、剧本、势力、城市、游戏日期、可见数值、人物列表、背景、窗口层级、消息、焦点、游标位置、动画时点及对应referenceId。尚未确定的值写待确认，不能替用户选择某个城市后宣称原版标准。

不能从同一截图确认的隐藏字段可以建立界面测试夹具，但必须标为synthetic，且不参与原版规则验收。

### 4.2 测量与实施

1. 标定有效画面、逻辑宽高、像素网格、显示比例与边框。
2. 使用左上角原点，测量窗口、地图、头像、文本、游标与遮挡。
3. 记录调色板、字格、字距、行距、页容量、选中与禁用样式。
4. 固定测试状态，先完成静态布局，再加入菜单、列表、数值输入和消息。
5. 在固定视口、DPR、逻辑时点下导出内部画布，生成并排、叠加与差异图。
6. 逐项修正，保存通过依据后冻结组件和网页回归基准。

不得仅凭“MD常见分辨率”写死本作主验收参数。资料未齐时，可在开发诊断页使用明确标识的可配置画布，但不能作为原版截图基准。

### 4.3 坐标表

| 字段组 | 必填字段 |
| --- | --- |
| 身份 | elementId、sceneId、referenceId |
| 几何 | x、y、width、height、逻辑像素单位 |
| 文本 | fontId、glyphAdvance、lineHeight、alignment |
| 绘制 | paletteId、layer、clip、visibilityCondition |
| 状态 | normal、selected、disabled等实际存在状态 |
| 动态 | frame／tick、持续时间、循环及依据 |

### 4.4 显示适配

固定内部布局，网页容器只负责缩放、居中和留边。清晰像素模式关闭平滑采样，优先整数倍放大；屏幕不足时整体缩小并记录显示适配。电视比例与原生像素网格分别存配置，验收截图不得混用。

M1-B通过条件：冻结场景的全部登记区域和操作已核对；无未说明占位；动态区域有时间基准；差异与例外均有记录。窗口能显示不构成还原通过。

## 05　素材、字体与声音施工

### 5.1 资源登记

每项资源登记assetId、用途、来源、制作方式、可用范围、原始尺寸、颜色／透明信息、哈希、版本和状态。采用能随网页分发的独立资源或有依据制作的资源；参考可查看不自动等于资源可随项目发布。

状态至少区分正式已核对、待核对、placeholder、停用。构建验收版时扫描场景资源依赖；正式还原区域仍有placeholder则阻止该区域通过，不能靠改标签消除问题。

### 5.2 头像、地图和图块

保留比例、轮廓、调色板与透明边缘。图块记录重复单元、转角、接缝、内边距及图层。图集打包保留整数尺寸，检查边缘采样、纹理间距和压缩；不能用缩放修正掩盖源图尺寸错误。

### 5.3 繁体中文字体

界面用字与名称遵循目标版本的繁体字形、异体字与标点。源码、网页、JSON、CSV统一使用UTF-8；显示文本与稳定ID分开。建立字符到位图字形的显式映射，不能从附件中的旧编码字节直接猜测全部字表。

先统计标准场景、数字、标点、菜单和消息所需字符，再扩展全量字库。系统繁体中文字体可用于画布外工具或开发诊断；画布内作为临时字体时标为placeholder。遇到缺字记录错误，不能静默替换成简体字或不同字形后算通过。

### 5.4 动画和声音

动画记录帧ID、顺序、持续时间、循环、停顿和遮挡。音乐记录曲目、场景、进入／退出、循环点与混音；音效记录逻辑事件、延迟、重叠、优先级与音量关系。

浏览器音频在首次明确交互后初始化，处理自动播放限制、静音、暂停与恢复。声音准备状态不改变规则结算；验证切换标签页、音频解码失败和资源缺失时的行为。

标准场景的画面、字形、音乐和音效分别验收。缺少原版音频时可完成事件接口，但声音还原状态保持未通过。

## 06　重建原版交互流程

### 6.1 统一逻辑输入

键盘、手柄和触屏转换为方向、确认、取消等逻辑动作，规则内核不读取DOM事件。物理键与MD按钮含义按版本资料填写；默认网页按键只是适配选择，不是原版证据。

区分按下、释放、首次触发、长按延迟、重复间隔、同时输入与失焦释放。若目标版本存在依赖输入时机的行为，记录其依据并建模，不能一律当作无关显示状态。

### 6.2 交互状态机

| 对象 | 必测状态 |
| --- | --- |
| 菜单 | 首末项、禁用项、循环／停止、打开与关闭 |
| 列表 | 单选／多选、翻页、排序、已选显示、返回位置 |
| 数值输入 | 位序、上下限、零值、越界、取消与确认 |
| 消息 | 逐字显示、跳过、完整显示、等待、连续消息 |
| 多层窗口 | 焦点所有者、遮挡、逐级取消、场景切换 |
| 输入异常 | 连按、失焦、触摸取消、手柄断开、窗口缩放 |

界面状态保存menuStack、cursor、selection、messageProgress及焦点。移动游标一般只改变界面状态；确认有效命令才进入规则执行。取消后是否保留选择和游标，按证据实现。

### 6.3 交互案例要求

每步至少记录：动作、按下／释放、相对逻辑时间、预期窗口、预期焦点、预期世界状态变化及参考时间码。时间单位在基准中锁定，未确认的延迟使用null并阻止节奏验收，不随意填经验数值。

通过条件：同一脚本重复达到同一窗口、焦点和结果；返回链完整；失焦不残留输入；异常输入不产生重复指令；关键路径有原版录像与网页回放对应。

## 07　工程架构与模块职责

### 7.1 技术选择与版本锁定

沿用原指南建议：TypeScript、Vite、Phaser；规则测试可使用Vitest，浏览器测试可使用Playwright。以上为待建立工程时锁定的方案，不表示依赖已安装或测试已执行。

初始化时选择彼此兼容的稳定版本，固定Node运行时、包管理器、框架和测试工具版本，提交锁文件与版本说明。统一一种包管理器，依赖安装使用冻结锁文件方式。不要在本文填入未经实际安装验证的版本号。

### 7.2 模块边界

| 目录 | 职责与限制 |
| --- | --- |
| src/core | 状态、命令、事件、随机与规则时钟；不依赖Phaser／DOM |
| src/rules | 战略与战斗计算；不做渲染和持久化 |
| src/ai | 读取获准信息，输出普通命令；不直接写世界 |
| src/presentation | 场景、窗口、地图、音画；消费状态与事件 |
| src/input | 设备适配、输入节奏、交互状态机 |
| src/persistence | 校验、快照、迁移、备份和导入导出 |
| src/devtools | 状态检查、回放、差异入口；不混入经典画布 |
| data、assets | 有稳定ID和清单的静态内容与资源 |
| tests、reference | 网页测试与原版证据分别存放 |

玩家和AI通过同一命令入口；渲染消费事件，不能决定结算次数。先使用清晰的主线程实现，只有测量表明运算阻塞后再引入Worker。并行化不能改变事件、随机或结算顺序。

以下是工程建成后应提供的统一脚本名，不是当前可运行命令。所有命令从项目根目录执行，并以非零退出码表示失败。

| 建议脚本 | 用途 | 完成要求 |

| test:data | ID、引用、范围与剧本校验 | 非法内容能被拒绝 |

## 08　状态模型与指令契约

### 8.1 分离状态

| 状态组 | 主要字段与要求 |
| --- | --- |
| 静态版本数据 | scenario、实体、规则与资源版本；只读 |
| 世界状态 | calendar、factions、cities、officers、relations |
| 任务与进程 | turnPhase、actorId、tasks、pendingEvents、eventFlags |
| 战斗状态 | battleId、units、terrain、objectives、phase、pendingActions |
| 随机与时钟 | rngAlgorithmVersion、rngState、rngCallCount、simulationClock |
| 界面状态 | sceneId、menuStack、cursor、selection、messageProgress |
| 浏览器设置 | 音量、网页键位、缩放偏好；不混入原版经济规则 |

### 8.2 命令入口

```text
GameCommand = {
  commandId, type, actorId, targetIds, params,
  issuedAtSimulationTick
}

execute(state, command, rules) =>
  { ok: true, nextState, events }
  | { ok: false, errorCode }
```

commandId用于日志和防重复处理；命令类型与参数采用可校验的联合类型。身份、时机、资源、目标、输入范围和引用有效性全部在提交前验证。不得只依赖菜单禁用状态防止非法调用。

默认失败不改变世界、任务和随机状态；目标版本若有失败也消耗资源或随机的规则，明确作为该规则的已执行结果建模。游戏内的行动失败与接口校验拒绝应区分，不使用同一个错误含义。

成功执行先计算候选状态与事件，通过完整性检查再原子发布。事件是表现结果的依据，不得让动画回调再次执行扣费。相同命令重复提交是否忽略，依赖commandId与处理记录决定；不同ID的连续合法行动按规则处理。

### 8.3 数值与不变量

为每个字段记录类型、单位、上下限、符号、取整、溢出与空值含义。未掌握原版算术时不能默认JavaScript浮点表达式与原版一致。

状态检查包括：实体ID唯一；引用存在；人物归属与身份自洽；资源合法；任务主体和目标有效；阶段转换合法；战斗与战略引用一致。合法资源上下限由规则表提供，不在通用检查器中凭经验写死。

### 8.4 回放与状态摘要

回放记录初始快照、规则／数据／构建版本、随机状态、按顺序执行的命令及必要时机。回放默认在独立内存状态运行，不覆盖玩家当前存档。

世界摘要按稳定ID和稳定键序序列化，明确数字、null与数组顺序；只排除预先列明的非规则显示字段。完整恢复测试另比较必要界面状态与待处理事件，不能用“排除了差异字段”的世界摘要证明全部存档等价。

## 09　战略系统施工清单

### 9.1 先登记原版菜单

下表用于研究分类，不是已确认的菜单名称与数量。建立功能台账，逐项记录目标版本实际菜单路径与referenceId；未核实项不直接变成已承诺的游戏机制。

| 分类 | 要核查的内容 | 边界 |
| --- | --- | --- |
| 开局 | 剧本、君主、难度、模式、人物创建 | 重选、无效组合、初始状态 |
| 内政经济 | 发展、收支、市场与税收等实际指令 | 投入、月份、取整、资源不足 |
| 人事 | 搜索、登用、任命、赏赐、移动等 | 身份、忠诚、人员占用 |
| 军事准备 | 募兵、训练、装备、编组、出征等 | 人口、兵力、行动资格 |
| 运输委任 | 运输、治理与持续任务 | 途中状态、归属变化、撤销 |
| 外交 | 谈判、关系变化、军事协作等 | 条件、期限、响应顺序 |
| 长期进程 | 出现、衰老、继承、事件 | 触发顺序、跨月、君主变化 |
| 胜负 | 灭亡、统一和结束 | 最后城市、最后人物、继续限制 |

### 9.2 单条指令规格

必填：commandId、菜单路径、执行身份、执行者条件、资源条件、输入范围、消耗时点、成功和游戏内失败结果、耗时、行动占用、随机依赖、消息、音效、取消路径、规则版本及参考案例。

至少提供成功、资源不足、无效执行者、输入上下界和取消案例；该指令实际不存在的分支标明不适用及依据。首条指令应选取证据最充分且前提可控制的一项，不凭“容易实现”决定公式。

### 9.3 月份推进

先绘制阶段图，查证行动、持续任务、财政、人物、事件与AI的实际顺序。这里不预设“先收税再发薪”等具体机制。为每个阶段定义输入状态、变更、事件、随机消耗和可保存边界。

月末指令使用可追踪的阶段与序号，避免失焦、重复点击或读档后重复结算。若保存中间阶段，需保存足够的游标和待处理任务；不能只保存月份数字然后重跑整月。

### 9.4 最小战略闭环

完成固定初始状态、选择城市与人物、执行一条已确认指令、展示结果、推进一次已确认月份、保存、读取并继续。比较不中断运行与存读档后运行的完整状态。

通过条件：所有选定指令与结算阶段有证据对应；失败和取消不产生额外变更；归属、资源、任务有效；跨月恢复等价。开发用临时经济模型只能在诊断模式出现。

## 10　战斗系统施工顺序

### 10.1 战略与战斗闭合

战斗输入必须来自经过校验的战略状态，明确出征人员、部队、物资、目标和状态占用。战后将损失、人物、俘虏、返回任务及城市归属作为完整规则结果写回，不能由演示界面直接修改归属。

| 顺序 | 需要落实的机制 | 最低证据 |
| --- | --- | --- |
| 1 | 出征、参战、资源与部署 | 战略进入战斗前后状态 |
| 2 | 网格、邻接、地形、通行、占位 | 可达、不可达与等成本路径案例 |
| 3 | 行动资格、移动、顺序、结束行动 | 完整一轮操作记录 |
| 4 | 攻击、计策及状态影响 | 条件、结果、取整与边界案例 |
| 5 | 时间、补给及已确认环境机制 | 时间推进与资源变化记录 |
| 6 | 胜利、失败、撤退、特殊终止 | 各分支和优先级 |
| 7 | 战后结算与战略恢复 | 世界状态与战斗状态一致性 |

### 10.2 寻路与计算

先确认目标版本的网格、邻接和成本，再选算法。通用A*或其他算法不自动保证等成本路径、移动顺序与原版一致。寻路结果应稳定可回放。

命中、伤害、士气和状态变化独立计算，记录输入、范围、取整、随机与结算时点。动画只消费事件；时机相关机制用显式逻辑时点建模，不交由不稳定渲染帧决定。

### 10.3 异常和完成门槛

覆盖无可用行动、目标失效、资源耗尽、撤退、同时满足多个结束条件、重复确认、场景切换及战斗中恢复。战斗中哪些状态可保存，先按第12章定义；不支持中途保存时不能生成半完成档。

首个战斗闭环必须从真实战略输入走到战后回写，并可重复回放。仅完成孤立战场不算M4通过。其他地图、兵种、计策和特殊规则按台账逐项扩展。

## 11　AI、随机机制与未知规则

### 11.1 AI权限

建议分为战略目标、城市执行与战场行动。每层读取明确的信息视图，通过普通命令执行。原版若存在特殊信息或资源待遇，需要独立证据；不能为了“更聪明”而默认全知或免费资源。

开发日志记录候选动作、筛选原因、评分依据、最终动作和随机调用摘要。该日志放在开发工具，不进入经典画布；规则版本改变时能说明决策为何变化。

### 11.2 规则研究协议

1. 写出待验证问题和可观察结果，区分事实与假设。
2. 记录全部可控制前提和不能观测的隐藏变量。
3. 一次改变一个关键变量，覆盖零值、临界值与上下界。
4. 保留每次原始结果、失败尝试、重复次数和采集方式。
5. 比较多个候选解释，使用未参与拟合的案例复核。
6. 记录支持范围、反例、剩余未知及下次实验。

少数样本只能支持局部结论，不能据此宣布完整公式。攻略、说明书和其他平台只作为带来源的假设，不直接覆盖本版本观察。

### 11.3 随机的三个层次

| 层次 | 通过含义 | 需要具备 |
| --- | --- | --- |
| 自身可重复 | 网页相同初态、种子和输入得到相同结果 | 固定算法版本、状态、调用顺序及恢复 |
| 分布相符 | 在指定条件下范围与频率符合对照 | 预先确定的实验、样本量和统计判定 |
| 序列相符 | 原版与网页逐次随机结果相符 | 原版算法、状态、调用顺序及必要时机的证据 |

样本量依事件频率、误差目标和可观测性设计，不预设统一次数。无法取得原版隐藏状态时，把序列相符标为待验证或证据受限，不承诺用录像自动推导全部随机机制。

开发可采用自有可序列化随机算法验证工程确定性，但必须命名为开发随机实现，并与原版一致性分开报告。不得因网页回放通过就关闭原版随机差异。

### 11.4 未知项收敛

为高影响项优先安排研究：结算顺序、跨月人物／任务、归属、伤害与随机调用。资料不足的区域保持可替换接口，未确认内容不批量扩散。每次里程碑复查未知项，明确哪些阻止后续阶段。

## 12　存档、浏览器与部署

### 12.1 存档结构与范围

使用IndexedDB保存结构化数据，提供文件导入导出。原版存读档菜单按目标版本复现；网页备份和额外槽位放在画布外。

档案至少包含：格式版本、规则／数据／参考／构建版本、saveId、slotId、revision、创建时间、完整状态、随机状态、待结算动作与必要界面恢复信息。浏览器墙钟时间仅用于管理显示，不代替游戏逻辑时间。

### 12.2 原子保存与一致性时点

只在已定义的逻辑一致性边界创建快照。默认包含命令提交完成后、稳定菜单状态与可恢复战斗阶段；消息动画等中途是否保存由策略明确决定。

在同一个IndexedDB读写事务中写入新快照、更新槽位指针和修订号，并保留上一份可用快照。预先完成序列化、校验和摘要计算；不要在事务中等待网络、音频等外部异步操作，以免事务失活。

事务失败保留旧指针，界面只有在事务完成后才提示保存成功。读取时验证结构、版本、引用、范围及摘要；摘要只能检查意外损坏，不是防篡改或来源认证。

### 12.3 迁移与导入

按版本逐步迁移，每步可测试；先保留原始备份，再迁移和校验。规则或数据变化不能仅靠结构迁移默认兼容，需有兼容表。不支持的版本明确拒绝，并保留原档用于后续处理。

导入限制文件大小、实体数量、嵌套深度和字段类型，校验重复ID、非法引用与数值。禁止执行导入内容或将其直接插入HTML。导入先落到新槽位，成功验证后再由用户选择使用，避免覆盖可用档。

具体大小与数量限制在数据规模明确后写入配置并测试；不能留作无上限输入。

### 12.4 多标签页与存储失败

每个槽位在同一事务中检查expectedRevision并更新revision，冲突时拒绝覆盖并提供重新读取或导出。可使用Web Locks协调，但需检测支持情况，事务修订检查仍作为一致性保障。BroadcastChannel可用于通知，不作为唯一互斥保证。

覆盖配额不足、数据库打开失败、事务中断、损坏记录、浏览器清理、标签页关闭和双标签竞争。保存失败保留内存状态与旧档，允许导出；不能把“浏览器一定保留本地数据”当承诺。

### 12.5 浏览器运行与发布

首阶段固定一个桌面主浏览器、版本、视口、DPR与键盘。其他浏览器、触屏、手柄、全屏、不同缩放和音频恢复分别扩展测试。支持矩阵报告实际结果，未经测试不宣称全面兼容。

首版静态站点使用HTTPS。构建产物与资源清单版本一致，避免新代码加载旧资源；可优先采用内容哈希资源与原子部署。基础版本稳定后再考虑离线缓存。

IndexedDB与站点来源关联。域名、协议或端口变化前提供导出与导入流程；部署回滚前同时检查存档版本。云存档不是单机玩法前置依赖。

通过条件：保存读取、导出导入与不中断运行等价；失败路径保护旧档；冲突不静默覆盖；迁移、拒绝、恢复及回滚策略均有实际测试。

## 13　对照验证与验收门槛

### 13.1 两套基准、三类检查

原版参考用于判断“是否还原正确”；已经通过原版对照的网页截图与回放用于防止回归。首次网页截图只能成为开发观察记录，不能直接当原版正确性证据。

工程检查验证程序可用；原版对照验证相符程度；内容检查验证覆盖范围。报告分列三者，不把构建通过写成玩法正确，也不把一次对照通过写成全内容完成。

### 13.2 阶段门槛

| 门槛 | 名称 | 必须具备 | 不代表 |
| --- | --- | --- | --- |
| G0／M0 | 资料可施工 | 版本、标准场景、操作与缺口可定位 | 代码已经完成 |
| G1A／M1-A | 工程可运行 | 锁定工具、构建、测试、诊断场景与功能请求可验证 | 画面已经还原 |
| G1B／M1-B | 标准场景对照通过 | 画面、字形、输入、返回与差异包通过 | 战略与声音全部通过 |
| G2／M2 | 最小战略闭环 | 已确认指令、月推进、状态与恢复等价 | 全战略规则正确 |
| G3／M3 | 战略范围通过 | 台账指令、长期结算与边界逐项通过 | 战斗已完成 |
| G4／M4 | 战斗范围通过 | 出征、战斗、终止和回写覆盖选定范围 | 全内容与AI已还原 |
| G5／M5 | 内容与行为范围通过 | 登记剧本、事件、AI、结束路径有覆盖证据 | 未验证隐藏机制一致 |
| G6／M6 | 发布验收通过 | 已声明范围、兼容、存档、恢复与发布材料齐全 | 超出声明范围的完整1比1 |

G1A可在G0尚有资料缺口时独立完成，但G1B不得绕过相关资料门槛。任何例外说明影响范围、责任人与到期点，不能把阻断问题改名为通过。

### 13.3 对照方法

| 对象 | 方法 | 通过依据 |
| --- | --- | --- |
| 静态画面 | 同裁切、同尺寸、同状态并排／叠加／差异 | 区域无未解释差异 |
| 动态画面 | 固定逻辑时点或连续帧 | 帧序、时长与遮挡有依据 |
| 交互 | 逐步动作与焦点断言 | 关键帧、返回路径、状态变化一致 |
| 规则 | 独立来源预期值与前后状态 | 成功、失败、边界与时序满足案例 |
| 存档 | 不中断路径与恢复路径比较 | 世界及必要恢复状态等价 |
| AI／随机 | 按第11章层次测试 | 仅声明实际达到层次 |
| 长期运行 | 多初态、多阶段与结束路径 | 无死锁、非法归属、丢人或坏档 |

### 13.4 视觉容差与环境

无损、干净、对齐参考可按区域设零差异目标。压缩或采集转换参考应分别核对几何、字形、内容和颜色，记录容差来源。不能整体提高阈值来掩盖局部错误。

动态遮罩需登记区域、原因与单独动态案例；不能遮住未修复元素。截图固定浏览器版本、操作系统、字体、视口、DPR、时间、测试状态及资源版本。截图裁切和缩放脚本应可重复执行。

### 13.5 报告与结果状态

每次报告包含代码提交、构建与工具版本、参考ID、输入、预期、实际、退出码、实际测试计数、图像／录像／回放及剩余差异。区分通过、失败、预期失败、跳过、阻断、未运行和不适用；零测试不构成验证。

丢档、卡死、非法状态、重复结算、未说明规则替代，以及声明范围内明显视觉／交互偏差阻止对应发布。缺陷修复后先验证复现案例，再运行受影响回归；不能直接覆盖旧基准使测试通过。

## 19　完全复刻目标与禁止偏离条款

### 19.1 本版执行目标

用户要求的是目标版本的UI和玩法完全一致，不是同题材游戏、现代化改版或外观近似的策略游戏。全部里程碑只是分批施工，不能把最终范围悄悄缩小为一个城市场景。任何阶段性演示都要说明未完成范围，继续完成后续任务。

“完全一致”落实为可检查的对象：每个画面状态、每个显示元素、每条输入路径、每个字段、每条规则、每个结算顺序、每种战斗分支、每个结束条件。对外声明必须受证据范围约束；测试通过不能证明尚未观察的隐藏行为一致。

采用独立网页重写路线，不将ROM或模拟器作为运行依赖。本版不因要求更严格而自动改成模拟器方案，也没有新增运行、解析或提取上传ROM的施工步骤。若今后改变研发参考方式，另行明确，不由执行AI自行扩大。

### 19.2 绝对禁止的替代行为

| 禁止事项 | 典型错误 | 正确处理 |
| --- | --- | --- |
| 自行设计UI | 添加卡片、渐变、现代按钮、自由布局 | 按已测量元素表绘制 |
| 通用字体冒充原版 | 因系统字体“差不多”就正式交付 | 使用核对后的位图字形；缺字作为阻断 |
| 凭印象补数据 | 自编人物能力、城市资源、剧本日期 | 录入来源明确的数据，不明处保持未知 |
| 猜公式 | 按其他三国游戏实现伤害、登用、内政 | 先建假设与实验，不把假设放入正式规则 |
| 简化菜单与流程 | 合并层级、省略消息、改变取消行为 | 逐状态、逐动作实现 |
| 修改玩法平衡 | 认为原版AI太弱、操作繁琐而优化 | 目标是复现；扩展必须独立且经范围决定 |
| 缩减最终范围 | 只做一个城市、一场战斗就宣告完成 | 阶段名称准确，继续登记功能台账 |
| 伪造验收 | 当前网页截图直接充当原版参考 | 区分原版证据、网页实际与回归基准 |
| 修改门槛 | 降阈值、加遮罩、跳测试消除红灯 | 修复实现，或报告证据不足的阻断 |
| 把随机说成一样 | 固定种子后宣称匹配原版 | 按自身、分布、序列三层分别验证 |

### 19.3 规范优先级

当前明确的用户要求优先，其次为锁定的目标版本证据及本书中的对应事实规格，再其次为工程实现建议。证据与规格冲突时创建冲突项，重新核对，不由AI任挑一种。

第19—30章把前18章的施工方法细化为本次严格目标的操作规程。前文允许标明局部差异交付阶段成果，不表示最终“完全复刻”允许保留差异。压缩参考上的容差只能用于研究比对，不能代替精确像素验收。

### 19.4 必须坦诚的边界

施工文档能约束过程，不能凭文字补出尚未采集的原版事实。没有足够参考时，AI可以独立完成资料索引、工程、工具和隔离开发；不能自行把待确认参数填成“原版就是如此”。遇到无法合法访问、无法观测或版本冲突的参考，记录具体缺口，继续不依赖它的工作。

当证据不足以判断某一隐藏机制时，结论是该项未证实；不能把“没有发现差异”升级为“所有情况完全相同”。最终报告必须包含有限测试的覆盖范围与仍不能证明的部分。

## 20　交给普通AI的启动与持续施工协议

### 20.1 交付包构成

除Word／PDF／Markdown正文外，本版附AI交付包。START_HERE.md给出启动顺序；AI执行约束.md可作为后续任务的约束来源；PROGRESS.md保存跨会话状态；templates提供资料与任务台账；tools提供离线结构检查和严格发布资料检查。

执行AI必须有文件读写、命令执行、依赖安装、浏览器运行与截图能力。缺少其中某项时先报告具体能力缺失，完成其余独立任务；只会聊天、不能执行代码的AI无法靠一份文档自行完成工程。

交付包不是游戏源码，没有安装Phaser，也没有实现原版规则。台账检查脚本验证资料结构与声明；另附compare_pixels.py进行无缩放、无阈值的PNG逐像素比较。这些工具均不替代真实游戏测试、证据真实性核查或完整游戏验收。

### 20.2 首次接手固定步骤

1. 阅读START_HERE、全文规范、当前PROGRESS和实际仓库说明；检查Git状态，保留已有改动。
2. 确认现有检出路径和运行工具，检查package、锁文件、脚本与测试；不存在则记为未建立，不假装已运行。
3. 扫描参考目录，按真实文件建立索引、哈希与来源；不把本书示例算作原版资料。
4. 对照baseline核查版本、显示、标准场景与输入，列出未知和冲突。
5. 建立功能台账与任务依赖，优先推进资料可核对任务及不依赖原版的工程任务。
6. 选择第一个依赖满足、范围明确、有可观察验收条件的未完成任务并执行。
7. 每完成一项，运行相关检查，保存实际产物与报告，更新台账和PROGRESS，然后继续下一项。

不逐任务询问“是否继续”。只有缺失权限、必要资料、无法推断的目标决定或不可用能力确实阻断所有有用工作时，才集中提出最小请求。不能因资料不全就擅自改成低标准产品。

### 20.3 单任务工作循环

取证 → 写明确规格 → 写独立预期与案例 → 实现最小范围 → 运行验证 → 定位差异 → 修复 → 重跑受影响检查 → 登记结果 → 选择下一任务。

写测试在先不是要求机械覆盖每个实现函数，而是先确定独立的预期结果。UI任务先有参考与坐标；规则任务先有案例与预期；工程工具任务先有能区分正确与错误的验收行为。

### 20.4 任务状态转换

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| todo | 已定义目标、范围和验收 | 依赖、资料与工具足够时进入in_progress |
| in_progress | 实际开始执行 | 有产物后进入verify；遇外部缺口进入blocked |
| verify | 已实现但尚未验收 | 检查全部满足后done；失败回in_progress |
| blocked | 写明缺失项与可解除动作 | 前提变化后重查，不能重复无效重试 |
| done | 任务范围内证据、产物、检查均满足 | 新证据推翻或基准变更时重新打开 |

任务done不自动使所属系统或里程碑done。开发演示可标工程任务完成，原版对照任务仍可blocked。禁止用“完成80%”替代实际台账。

### 20.5 跨会话恢复

会话结束前更新PROGRESS：当前提交与工作区变更、已完成任务、执行命令和退出码、运行进程、报告路径、参考版本、未知项、下一可执行任务。下一会话先核实这些状态，不能仅相信文字。

保留失败日志与回放，不只保存成功截图。文档与代码一起做小步版本记录；不为了整洁删除失败证据或重置用户改动。恢复后继续未完成目标，不把每次新会话当作允许重做UI设计。

## 21　逐屏UI规格编制与像素还原

### 21.1 先建屏幕目录

按实际目标版本遍历启动、标题、开局、战略地图、城市、人物列表、指令输入、消息、战场、战后、存读档与结束等流程。类别仅供检查；最终屏幕ID、数量与名称必须来自实际参考。

每个屏幕使用稳定screenId，每个变体使用stateId；不是“一张城市图”就代表所有城市菜单。以菜单、页码、选中项、消息进度、数值位序和动画阶段区分状态。

### 21.2 每屏必填规格

| 规格组 | 必填内容 | 缺失后果 |
| --- | --- | --- |
| 版本与参考 | baselineId、referenceId、原图哈希、状态与帧／时间码 | 不能判定同版本同状态 |
| 画面空间 | 有效区、逻辑宽高、像素／显示比例、边框 | 不允许精确布局验收 |
| 元素树 | elementId、父元素、层级、遮挡、裁切与显隐条件 | 不允许凭视觉印象排版 |
| 几何 | 整数坐标、尺寸、锚点、文本起点与对齐 | 不允许百分比猜测 |
| 颜色 | 调色板值、索引、用途及颜色转换依据 | 不把视频压缩色直接当原版色 |
| 字形 | glyphId、字格、字距、行距、标点、缺字策略 | 不允许默认字体正式交付 |
| 内容 | 文本、格式、补零、负号、溢出、换行与截断 | 不擅自使用浏览器自动排版 |
| 状态 | 普通、选中、禁用、焦点、闪烁及各自资源 | 不只做正常状态 |
| 动态 | 帧序、逻辑时刻、时长、转场、光标周期 | 不用CSS默认动画近似 |

每个元素至少对应一个测量记录。重复图块、边框、文字和游标先做共用组件，通过后所有屏幕引用同一实现；不允许每个窗口另调一套近似样式。

### 21.3 标准测量步骤

1. 保留原始文件，只在副本进行处理；先记录尺寸和压缩情况。
2. 确认有效画面与裁切框；同一规则应用所有参考，不逐张“调到像”。
3. 标出整数网格，测每个矩形边缘、文字首像素、图块周期和透明区。
4. 用水平／垂直扫描核查重复边框和间距，不用整体截图缩放掩盖局部偏移。
5. 比较同控件不同状态，分离固定背景、变化内容和动画。
6. 把测量值写入元素表与资源清单；每个值标参考或推断，推断未验证不能通过。
7. 导出标注图，另一轮从原图重新核对关键尺寸；保留冲突而非平均取值。

### 21.4 绘制顺序与渲染稳定性

绘制顺序由参考确定，至少明确背景、地图／头像、窗口、文字、选中态、游标和遮罩。顺序清单仅是检查维度，不能先验断言所有画面都采用相同层次。

游戏内部禁止浏览器响应式重排。Phaser纹理过滤、相机偏移、坐标、分辨率和CSS缩放须显式配置并实测；整数采样不能只写一个pixelArt选项就算验收。Canvas与WebGL输出若不同，固定主验收渲染器并记录兼容结果。

关键截图使用逻辑画布像素导出，网页全屏截图另外验证容器。跨设备显示大小可以不同，内部像素布局和状态不能变化。关闭无关时间、光标与随机性依赖，动画在明确逻辑时刻采样。

### 21.5 文本与字库专项

收集所有屏幕、人物、地名和消息用字，保存实际繁体、异体、标点、半角／全角差异。不要自动繁简转换、Unicode替换或修正“看起来错”的原版写法。

字形映射按glyphId而不是系统字体回退；文本规格包含数字占位、姓名长度、空格、颜色、文本区域与逐字节奏。动态文本测试最短、最长、最大位数、空列表、满页与跨页；只核对默认数值无法证明字库和排版完整。

位图字形可以独立重建，但逐字有参考与差异；不能用AI生成一套“像素风中文”代替。资源不可用或缺细节时记录阻断，不把风格相似视为字形一致。

## 22　像素比较、差异定位与基准保护

### 22.1 精确验收前提

无损、无未知缩放、无未解释色彩转换、同逻辑尺寸、同画面状态的参考，才可作为逐像素精确验收输入。录像截帧、拍屏和有损图片可以辅助测量与研究；未恢复可信像素前，不承担零差异证明。

先确认版本和状态，再对齐。禁止任意透视、非整数重采样、颜色“美化”或局部变形把差异抹平。若目标包含电视显示效果，先冻结可复现的显示变换，再比较其结果；不可逐图调参数。

### 22.2 比较器必须报告

| 指标／产物 | 要求 |
| --- | --- |
| 输入元数据 | 双方哈希、尺寸、通道、基准版本、场景与采样时刻 |
| 差异像素数 | RGB或已定义RGBA空间逐像素统计，不只报告平均分 |
| 最大通道差 | 明确像素值比较方法与颜色空间 |
| 差异包围盒 | 标出偏移发生的位置，不用整体相似率概括 |
| 区域结果 | 元素／窗口级差异，不把大背景稀释小文字错误 |
| 图像产物 | 原图、实际图、并排、叠加、热力图与测量标注 |
| 判定 | exact通过、失败或证据不足；不能混为一个百分比 |

透明图像需固定背景合成规则或显式比较alpha；不能随工具默认值改变结果。截图不得包含浏览器工具栏、网页辅助控件或未冻结的鼠标指针。

### 22.3 精确模式门槛

已锁定的精确参考区域要求差异像素数为0。任何非零差异都定位并解释，正式完全复刻验收不以调大阈值通过。颜色来源不确定时，该区域为证据不足，不能当作“允许误差”。

动态区域不是永久豁免区。静态截图可暂时遮罩，但每个遮罩必须有登记ID、原因、区域和独立动态案例；最终覆盖表应确认全部遮罩已由对应动态测试承担，不留下无验证区域。

没有可信原像素时，只能给出布局、字形或内容的分项核对结论，不宣称逐像素一致。此限制对所有AI有效，不由模型自信程度决定。

可直接运行交付包tools/compare_pixels.py：输入锁定参考PNG与网页实际PNG，输出差异像素数、包围盒、并排、叠加与差异图。依赖和退出码见tools/README；该工具不验证参考真实性、场景状态或采样时刻，也不擅自缩放、调色或覆盖基准。

### 22.4 固定修复顺序

先修版本与状态不一致，再修裁切／显示比例，再修整体原点和窗口几何，再修图块／头像，再修字形与文字排版，最后修颜色、动画与局部边缘。前一层错误未解决，不通过局部拉伸抵消。

每次修复保留前后差异图，运行所有使用该共用组件的屏幕回归。某城市修好而其他城市坏掉不算修复完成。

### 22.5 基准不可被实现自证

原始参考只读保存，变更需要新的referenceId和原因。网页回归基准只有在对应原版对照通过后才标记accepted；先前开发截图标记development。

更新基准时生成旧基准、新基准、原版三方比较，说明为何更正确。开发AI不能仅因为测试失败就执行批量更新截图，不得把增加遮罩、放宽阈值或删除案例计为修复。

## 23　菜单状态图与全部输入分支

### 23.1 逐节点建模

每个窗口、列表、消息、输入框和转场都是状态图节点；边记录逻辑动作、触发条件、目标、焦点、游标、世界变化、消息与耗时。存在同一画面不同内部状态时使用不同stateId，不靠截图文件名猜。

示例写法仅说明规格格式：从CITY.IDLE收到某动作进入MENU.OPEN，具体动作、菜单名与默认选择必须由原版记录填写。不能把此示例直接当作本作真实流程。

### 23.2 每个菜单的完整分支

菜单至少核对进入来源、初始游标、首末项、横纵移动、循环／停止、禁用项跳过或停留、确认、取消、关闭后焦点和重复进入位置。若某分支不存在，记录证据支持的不适用。

列表核对页容量、翻页、页码、排序稳定性、单选／多选、已选取消、空表、满页、末页和返回。数值输入核对编辑顺序、位序、进位、上下界、重复输入、确认与取消。消息核对逐字、快进、等待、下一条与输入消耗。

### 23.3 时间与输入采集

记录按下和释放，区分单次触发与保持。长按延迟、重复间隔、消息速度和转场周期用实测区间记录；不能从低帧率录像声称精确到无法分辨的时刻。

网页采用固定逻辑时钟，渲染帧率不改变操作次数。若输入采样本身影响原版随机或结算，保存相应时机；不能用“UI不影响规则”的默认假设抹去已观察行为。

### 23.4 生成测试路径

对状态图列出所有节点与边，先覆盖每条已登记边，再覆盖嵌套返回、连续确认、跨页返回与异常中断。路径必须能从固定初态执行；测试中直接跳到窗口的方式只验证局部，不替代完整用户路径。

状态图覆盖率只针对已登记范围；所有节点通过仍不证明没有遗漏原版菜单。另用第29章的功能普查核对分母。交互脚本同时断言画面、焦点、世界状态和事件，防止“图像一样但操作结果错”。

## 24　玩法规格、公式研究与数据闭合

### 24.1 每条玩法必须先有规则卡

| 规则卡字段 | 必须写清的内容 |
| --- | --- |
| 身份 | ruleId、目标版本、实际菜单／触发点、referenceIds |
| 前提 | 阶段、执行者、目标、资源、关系、资格、任务占用 |
| 输入 | 字段类型、单位、允许范围、顺序与取消行为 |
| 判定顺序 | 多个条件同时不满足时先出现什么结果 |
| 消耗 | 何时扣除、扣谁、失败是否消耗、是否可重复 |
| 结果 | 每个被改字段、人物／城市归属、任务与事件 |
| 算术 | 符号、整数宽度、取整、截断、溢出、上下限 |
| 随机 | 调用条件、顺序、范围、不能观测的状态 |
| 表现 | 原版消息、动画、音效及输入锁定阶段 |
| 恢复 | 提交边界、读档后如何继续、不能保存的状态 |
| 依据 | 原始记录、反例、验证层次、剩余未知 |

缺少关键字段时，不用“符合常识”补齐。可以先做规则接口和校验器，但不能将开发公式写入正式rulesVersion。

### 24.2 必备决策表

为每条指令列条件组合与结果，至少覆盖：完全满足、单项不满足、多个条件同时不满足、资源恰好够、少一单位、输入最小／最大、越界、目标失效、同目标连续执行与取消。是否适用按实际指令决定。

条件组合不能全部枚举时，用边界、等价类和交互组合选例，并记录未覆盖组合。组合测试是降低漏测风险的方法，不是证明所有输入都一致。

### 24.3 推导公式的操作步骤

1. 从参考提取完整前后状态，不只抄最终收益。
2. 在可控范围改变一个输入，并保留其他条件；隐藏变量记录为限制。
3. 选择能区分候选公式的输入，特别是取整边界和阈值两侧。
4. 单独观察消耗时点、失败分支、作用对象和消息顺序。
5. 拟合只是候选解释；使用未参与拟合的案例检验。
6. 有反例就缩小结论范围或推翻公式，不把异常删掉。
7. 若多个公式仍无法区分，规则状态为待验证，明确下一判别实验。

不得从一两次结果断言“收益等于能力除以某数”。也不得把其他平台公开公式直接写入本作而省略验证。

### 24.4 月度、年度与事件顺序

为每个时间边界建立有序阶段表，记录每阶段读写字段、参与对象、遍历顺序、随机调用、触发事件及可保存点。阶段名称和顺序来自目标版本证据，不采用本文预设经济模型。

重点观察同月多任务、资源不足、人物变化、势力消失、事件相互影响与结束条件冲突。规则引擎要能从指定边界继续，恢复不能重复执行已经提交的阶段。

### 24.5 数据不是装饰

剧本、人物、城市、关系、地图连接、地形和事件表分别建稳定ID。每个字段记录来源和状态；未确认数据不能因“UI需要显示”而自动成为正式初始值。

整表核对包括总数、重复、缺失、引用、归属、上下界、同名与异体字。不同剧本之间同一人物的不同值分别验证。数量尚未核实就保持未知，禁止从互联网随意找一份全平台混合数据充数。

## 25　战斗与AI专项施工规程

### 25.1 战斗拆成可验证子系统

按出征资格、人员与资源锁定、部署、地图、移动、行动、攻击、计策、环境、补给、时间、终止、俘虏与战后回写拆卡。每个子系统必须引用实际目标版本资料；本文列的是核查维度，不断言本作含全部机制。

每张战斗地图登记尺寸、格型、邻接、地形、通行成本、阻挡、占位、部署与胜负目标。地图截图与游戏规则连接表分别维护，视觉可走不代表规则允许走。

### 25.2 移动与行动决策表

覆盖零移动能力、恰好可达、差一单位、障碍、己方／敌方占位、等成本路径、地图边缘、目标离开、移动后剩余行动、取消及结束行动。寻路要验证实际选择路径，不只验证存在某条可达路径。

行动计算与动画分离，但保留证据支持的时机。确认动作只提交一次；动画加速、失焦和浏览器低帧率不能产生额外攻击或扣费。

### 25.3 战斗结束事务

对胜利、失败、撤退及证据支持的特殊终止分别定义结果。结束时先形成完整候选结果，再同时更新部队、资源、人物、任务和归属；失败不能留下“一半已回战略，一半还在战斗”的状态。

测试战前保存、可保存战斗阶段、结束前后恢复、重复结束触发和世界对象失效。战斗结算必须与对应战略初态及原版前后案例配对。

### 25.4 AI不能用“合理”代替“一样”

记录观察到的行动顺序、候选、放弃条件、目标、数量、资源变化和结果。测试数据包含不同资源、关系、地图、时间及其他能区分假设的状态。无法观测的内部评分不可伪写成已知原版算法。

自制AI可以作为独立诊断实现验证接口，但正式AI对照未通过时保持阻断。相同可见状态的重复录像不自动保证隐藏状态相同；报告应限定结论，不把差异一概归为随机。

### 25.5 随机日志最小集

网页记录算法版本、种子／状态标识、调用序号、调用原因、范围和返回值，避免把随机数消耗藏在绘制或日志代码中。规范化回放应在不同渲染帧率下产生同一规则轨迹；若原版时机影响规则，则测试显式包含该时机。

仅比较随机摘要不能证明与原版相同。严格目标中的原版分布或序列验证仍需要可观察对照；无法取得时，不允许在最终报告勾选全部玩法一致。

## 26　自动验收工程与阻断规则

### 26.1 验收流水线

工程建立后串联：类型与构建 → 数据／资源引用 → 规则单元与边界 → 存档与回放 → 浏览器交互 → 精确画面／动态 → 产物运行 → 台账与声明一致性。各阶段保存独立报告，失败保留原退出码。

构建成功只解锁后续测试，不给玩法正确性背书。测试失败分为实现错误、环境故障、证据缺失与规格冲突；分类不能替代修复，相关门槛保持失败或阻断。

### 26.2 测试的可信来源

规则预期来自独立原版观察，UI预期来自锁定参考，存档预期来自不中断路径与恢复路径等价，不变量来自明确状态约束。可以使用网页自生数据做工程测试，但要标明来源，不能算作原版对照。

防止“实现与测试一起错”：规则函数不能同时生产自己的唯一expected；视觉测试不能边运行边把actual覆盖expected；同一个未知公式不能以两个复制函数互证。

### 26.3 浏览器测试固定前提

锁定浏览器与测试工具版本、操作系统、渲染器、视口、DPR、语言、时区、资源、测试初态与逻辑时刻。等待明确就绪信号与断言，不靠任意长等待掩盖竞态。

就绪至少包括资源成功加载、场景状态正确、输入可用和测试初态安装完毕。页面没有报错或端口打开不足以证明功能可用。录制关键路径时同时保存状态和事件摘要，便于分辨视觉与规则差异。

### 26.4 故障注入与长期运行

存档测试注入事务失败、容量不足、坏档、旧版本、双标签冲突和中断。输入测试覆盖连按、失焦、页面恢复和手柄／触摸中断。部署测试验证资源版本一致及回滚读取策略。

长期运行使用可复现种子、多个初态和边界状态；每步检查资源、引用、归属与阶段有效性。失败保存最小回放并缩减复现。跑很多月无崩溃证明稳定性，不替代原版数值和AI对照。

### 26.5 严格发布阻断

存在以下任一项，不可声明完全复刻：原版范围未普查；关键参考缺失或冲突；正式场景占位；精确区域非零差异；未验证动态遮罩；玩法规则无独立证据；必测失败／跳过／零测试；随机或AI声明超出证据；丢档、非法状态或重复结算。

工程演示和阶段成果可以交付，但必须准确标注，并继续后续任务。阻断不通过修改通过条件解除，必须补证据或修实现。

### 26.6 本交付包检查器的用途

tools/validate_handoff.py不依赖第三方库。structure模式检查JSON、记录ID、引用和任务依赖；exact-release模式检查发布前证据与覆盖，暂不要求正在执行的发布汇总任务和部署后任务先完成；delivered模式检查线上报告及其余必需任务，仅不要求最终交付汇总任务先完成自身。初始模板的structure可以通过，exact-release应失败，因为实际资料和游戏尚未完成。

检查器不验证原版真实性、库存是否穷尽、截图是否真为零差异或测试是否伪造。实际项目必须实现并运行以上测试。即使有人把模板字段全改成passed，也不能据此获得真实的完全复刻结论。

### 27.2 依赖调度规则

每轮选择依赖全为done、资料足够且无阻断的最高优先级任务。资料任务可以和独立工程任务交错执行；同一人或单个AI也按此规则顺序推进，不要求多代理。

被阻断任务写明具体缺口与解除动作。若存在可执行任务，继续工作；不要把整项目停在一个未知伤害公式上，也不要跳过公式验收直接宣布战斗完成。

### 27.3 完成证据

每张任务单给出输入文件、允许修改路径、实现范围、禁止项、测试命令、预期观察和报告位置。没有实际报告就不能done；截图任务必须有图，规则任务必须有数值和状态，恢复任务必须有对比路径。

最终交付必须聚合所有登记功能与屏幕的完成状态，不按任务数量计算产品还原比例。可把很小工程任务拆成许多项，但不能用这些done数量稀释未完成玩法。

## 28　AI自检、偏离预警与返工协议

### 28.1 每次改动前自问

这是原版已有行为还是我设计的？依据在哪个referenceId？修改会影响哪些共用屏幕、规则、存档和回放？有没有用临时数据或字体？独立预期是什么？哪些事情我还不知道？

答案不完整时先补任务规格或把未知隔离；不能把模型熟悉程度当证据。用户明确要求完全复刻，不授权开发AI自行决定“更好用”的替代。

### 28.2 发现偏离的处理

| 偏离 | 立即动作 | 恢复施工条件 |
| --- | --- | --- |
| 现代UI混入经典画布 | 停止复制该组件，列受影响屏幕 | 按元素表重做并回归 |
| 错版本资料混入 | 标记冲突，隔离依赖数据与基准 | 来源与目标版本核对完成 |
| 未确认公式进正式规则 | 撤出正式规则版本或标阻断 | 独立案例充分且边界通过 |
| 假素材冒充原版 | 追踪全部引用，恢复placeholder状态 | 真实核对与来源完成 |
| 自动更新基准掩盖差异 | 保留更改前文件，恢复可信基准 | 三方比较证明更新正确 |
| 交互简化 | 打开原版状态图逐边定位 | 完整流程及返回路径通过 |
| 假通过／空测试 | 撤回完成声明，查报告与退出码 | 实际执行有意义检查 |

只回退本次引入的错误，不清除用户其他工作。修复后更新规则版本或资源版本及受影响基准，记录原因和复现。

### 28.3 开发者与验收者是同一个AI时

分两个回合处理：先冻结证据与独立预期，再实现；验收回合从原始输入重新运行，检查报告产物与实际文件。验收时不能修改expected、阈值和遮罩来获得绿灯。

同一个AI的二次审查只是降低遗漏，不能视为独立原版证据。证据来源与可重复测试必须真实存在，不因“我已经仔细检查”而省略。

### 28.4 工作结束的判断

全项目只能在目标范围全部登记、完成、对照与恢复通过，且声明不超证据时报告目标达成。若外部缺口使所有有用工作耗尽，报告已完成能力、精确阻断与最小补充资料；不能报告完全复刻完成。

若会话资源不足，保存可恢复的PROGRESS和下一任务。这是阶段性交接，不是把剩余开发责任退回用户，也不等于减少原目标。

## 29　全量普查、覆盖矩阵与最终验收

### 29.1 三份独立清单

维护屏幕／状态清单、功能／规则清单、数据／资源清单。三者互相引用：一个功能会触发哪些屏幕、使用哪些数据和素材；同一窗口被哪些功能共用。只有单个功能列表无法发现字体缺字和隐藏返回路径。

普查从所有可观察入口出发：逐项进入菜单、列出条件显示项、遍历列表与消息、记录开局和结束分支、观察不同城市与战斗类型。不能只用当前网页已经实现的按钮反推原版功能分母。

### 29.2 覆盖矩阵

| 行维度 | 必须关联 | 必须报告 |
| --- | --- | --- |
| 屏幕状态 | reference、元素、资源、操作与动态case | 精确／内容／动态分别结果 |
| 输入边 | 源状态、条件、动作、目标与焦点case | 已登记边、已执行边、失败边 |
| 规则分支 | 规则卡、决策表、输入与expected | 成功、失败、边界及冲突 |
| 数据字段 | 实体、剧本、来源和校验 | 已核对、未知、冲突 |
| 存档边界 | 版本、阶段、恢复与失败case | 等价、异常、冲突与迁移 |
| AI／随机 | 初态、观察、验证层次和限制 | 自身、分布、序列分别状态 |

引用断链、没有案例的正式功能、只有工程测试的原版规则、没有动态覆盖的遮罩，都要自动列为问题。

### 29.3 完全复刻声明的检查顺序

先核对范围分母来自原版普查且未擅自删项，再核对全部记录有来源，再检查像素和规则报告，再检查恢复、兼容与产物，最后撰写结论。顺序不能反过来先宣称“完整”再挑几个演示证明。

即使有限测试全部通过，仍需明确未能观察的隐藏状态和未能证明的随机层次。严格目标不允许把未证实项打勾；若这些项仍存在，就继续研究或准确报告证据限制，而不是出具不实的完全一致保证。

### 29.4 最终验收包

包含原版版本与采集说明、完整清单及修订历史、全部参考索引、实现代码与构建锁定、资源来源、逐屏报告、规则案例、动态与交互录像、AI随机结论、长期回放、存档恢复、兼容矩阵、发布回滚和已知差异。

产物运行验收从全新浏览器状态开始，走开局、城市、战略、战斗、存读档与结束的代表路径；原版精确验收同时保留逐项证据，代表路径不能替代全量清单。

## 31　开发前输入验收与剩余缺口

### 31.1 本次审查结论

### 31.2 最小输入关口

| 关口 | 必须填齐 | 通过物 | 当前状态 |
| --- | --- | --- | --- |
| 版本 | 实际繁体画面、来源、修订识别范围 | 版本说明与标题参考 | 用户指定，实证待补 |

未通过关口不阻止基础工程、工具和数据模型开发，但阻止对应还原声明。若目标版本本身无法识别到精确修订，记录可确认范围，不把附件日期或地区头当作全部证明。

### 31.3 先冻结事实，再批量开发

首先完成一个城市状态的真实规格，验证采集、字形、显示和操作方法，再按同一方法扩展。全量内容不能由一个样例自动推断。把缺口分为可自主检索、需新增观察、需权限、无法观测四类，给下一步动作和影响任务。

资料有新结论时更新baseline和相关规则版本，重新打开受影响任务。不能因为已经写了很多代码而坚持未经证实的公式。

### 31.4 “一次开发跑通上线”的含义

本项目以一次完整交付周期贯通取证、开发、测试、构建、部署和线上复测为目标，执行AI持续修复而不把每个阶段退回给用户。它不表示禁止迭代、禁止返工或可以省略研究。若把“一次”理解为一个提示词或一次生成，就无法诚实保证复杂原作的全部行为一致。

最终仍按全量复刻目标交付，不能以可部署的占位网页、工程演示或最小闭环冒充完成版。若外部资料确实不可得，应报告确切阻断，而不是制造一个“能上线但玩法不对”的替代品。

## 32　空仓库到可启动工程的固定契约

### 32.1 工程位置与运行环境

应用位于仓库根目录，使用现有Git检出；文档保留docs，游戏源码src、静态资源public或经构建导入的assets、原版证据reference、测试tests、产物dist分别存放。原始私有参考不能直接放入public或被产物打包。

本次云环境实际观察到Node v24.22.1、npm 11.9.0、Python 3.12.14，可作为ENG-001初始工具基线。尚未安装验证游戏依赖组合；不将观察到工具存在写成Vite／Phaser兼容已通过。

初始化时将Node写入.node-version，将npm版本写入packageManager，依赖选定并锁定实际版本，生成package-lock.json。Node24.22.1与npm11.9.0为本版默认候选；若实际兼容检查失败，按官方支持范围调整并记录，不静默浮动。

### 32.3 首次启动与干净重建

开发者从干净检出安装、启动、进行代表交互并构建；再从同一提交的另一个临时副本执行npm ci和构建，验证不存在未提交的本地资源依赖。不要删除用户工作区来制造干净环境。

就绪信号至少包含入口成功、资源已加载、场景可输入、正确baseline和游戏状态。浏览器控制台错误、资源失败、黑屏、缺字和无响应都必须诊断；端口打开不等于游戏可用。

工具虚拟环境、node_modules、测试缓存和dist不作为源码提交。产物通过发布归档保留；构建过程不改写原始参考与既定基准。

## 33　先贯通纵向闭环，再扩展全内容

### 33.1 修正原任务依赖

v2.0把完整战斗安排在全部战略之后，可能让系统集成问题过晚暴露。本版新增CORE-INTEGRATION、BATTLE-MIN、VERTICAL、DIST、OPS和LIVE任务：早期先做一条有证据的真实闭环，再填满全部战略和战斗内容。

不得要求先完成全部人物、剧本和AI才首次运行应用。也不得因闭环通过就关闭全量复刻目标。早期诊断可用明确的synthetic状态，但正式对照闭环必须采用可追溯初态与规则。

### 33.2 集成路径

固定已确认初态 → 开局选择 → 城市查看 → 菜单进入与返回 → 执行已确认指令 → 月份推进 → 出征 → 最小战斗 → 战后回写 → 保存 → 关闭页面 → 重开读取 → 继续相同命令。

某段缺少原版证据时，将该段还原验收标阻断，继续验证不依赖该规则的工程接口；不能填一个简化战斗来宣称整条原版路径已通过。

### 33.3 贯通路径要检查什么

每一步同时核对图像、焦点、世界字段、任务、事件序列和随机状态。分别跑不中断路径与存读档路径，比较必要完整状态。对战斗回写、月末和保存边界加入重复确认、失焦与中断，验证不重复扣费或结算。

最终全量验收增加胜负与结束、其他剧本、其他城市、其他战斗机制和长期事件。罕见分支可用独立测试夹具构造前提，但夹具不应替代真实规则来源，也不应成为玩家默认世界。

### 33.4 对开发AI的连续交付要求

每个提交保持已完成路径可运行；合并共用组件前重跑全部受影响场景。工作按依赖持续推进，不因演示可以播放就结束，也不等待用户逐段补一句“继续”。

## 34　静态产物、版本与资源路径

### 34.1 唯一可部署目录

只部署经过测试的dist，不部署仓库根目录、docs、reference、测试夹具、上传附件或开发缓存。默认采用静态网页，不增加账号、数据库或服务端作为单机运行前置条件。

构建产物至少包含index.html、带版本／内容哈希资源和release-manifest.json。所有运行所需字体、头像、地图、音频与数据本地随包提供，不依赖开发服务器或未冻结的第三方CDN。

### 34.2 发布清单契约

release-manifest.json包含schemaVersion=1、完整源码commit、唯一buildId、构建时间、basePath、entry、rulesVersion、dataVersion、assetsVersion、Node／npm版本和files。files以产物相对路径为键、SHA-256为值，覆盖除清单自身外的每个发布文件。

不把清单自身摘要递归写入files。清单由构建程序在全部资源生成后创建，读取实际文件计算摘要；不能手工填全零或旧构建哈希。源码提交、实际构建输入和发布产物对应；脏的应用源码或资源不得冒用干净提交身份。编译输入在本轮验证中冻结，允许新写acceptance报告与本轮台账状态，但必须列出这些输出路径，不能将游戏源码或正式资源放进豁免范围。

verify:release开始前在project.candidate分配本轮完整commit、唯一buildId和basePath，全部真实报告与最终产物使用同一身份。检查器拒绝缺失或其他构建／提交的报告；不能借用以前绿色结果。

buildId应在画布外的网页诊断入口可查，线上检查同时读取清单和实际运行版本。敏感配置不进入前端；本项目默认静态玩法不需要浏览器保存GitHub凭据或部署令牌。

### 34.3 根路径与项目子路径

默认GitHub Pages项目地址采用/sanguo3/；自定义域名或其他静态站点可以采用/。Vite base、Phaser资源加载、数据fetch、字体和音频URL均按同一构建基址解析，禁止散落硬编码/assets或/src。

使用构建导入或import.meta.env.BASE_URL统一生成资源路径。默认以单页面游戏内部状态切换场景，不引入需要服务器回退规则的浏览器history路由。若使用路由，静态站点优先明确hash路由并测试刷新；不假定GitHub Pages提供任意路径回退。

分别在/和/sanguo3/下构建与运行测试。根路径通过不能代替子路径；不能只改index.html引用而漏掉动态加载头像、地图、字库与声音。

### 34.4 静态检查与浏览器检查

交付包tools/verify_dist.py检查清单、文件摘要、入口资源路径和禁止目录混入，支持普通包和GitHub Pages模式；它不会运行游戏或证明UI／玩法正确。脚本自测使用人工生成网页，不是游戏上线证据。

浏览器必须继续测试实际产物：入口、所有资源请求、字形、音频初始化、开局、闭环、保存恢复、缩放、刷新与错误提示。不能用静态工具通过替代test:dist或test:live。

## 35　默认上线方案与GitHub Actions模板

### 35.1 默认方案

默认部署到本仓库GitHub Pages项目站点；需先确认仓库计划和设置支持Pages，并将Pages构建来源设为GitHub Actions。该设置是否已开启当前未验证，文档模板不代表已创建站点。若Pages不可用，保留相同dist契约选择其他静态托管，不擅自增加后端。

本版不实际部署网站：仓库尚无游戏应用。提供的workflow保持.example后缀，位于文档模板目录；只有实现脚本、补齐门禁并配置Pages后，实施任务才将它安装到.github/workflows。

### 35.2 构建与部署顺序

检出指定提交 → 固定运行时与锁文件 → 安装浏览器和测试依赖 → 执行verify:release（源码检查、以/sanguo3/基址构建、test:dist、清单检查、exact-release依次完成）→ 上传同一dist → Pages部署 → 运行test:live并核对buildId。

PR仅构建和测试，不部署；main推送在上述条件全部通过后才部署。构建job与部署job是独立机器：模板以delivery-state构建附件传递同一dist、当前台账和报告；部署job恢复后重新取得授权原版资料，不能重新读取旧台账而丢失本次结果。线上报告另存附件，不默认把运行状态自动提交回Git。原始私有参考不进入公开站点或公共构建附件，证据通道和可见范围需在OPS-PREP实际确认。

不可通过continue-on-error、删除门禁或将失败任务改为可选获得发布。原版证据若不能公开，先配置可访问且受控的CI资料渠道，缺失时保持阻断，不把缺参考变成跳过。

exact-release依赖本轮dist报告，因此必须在本轮构建与产物测试之后执行；不得用旧构建报告提前过门禁。门禁后不再构建，上传与部署的必须是刚测试的同一产物。

### 35.3 工作流固定与权限

使用完整commit固定Actions版本，记录官方来源与适用运行时。随包模板的checkout、setup-node、configure-pages、upload-pages-artifact和deploy-pages引用已在本次修订时读取官方Git标签及action.yml核对，详见actions-pins.json。

本次只做来源与模板结构检查，没有在GitHub真实执行该工作流。部署job需要pages:write与id-token:write，普通构建job仅contents:read。PR不获得部署权限，也不向浏览器暴露GITHUB_TOKEN。

GitHub托管Ubuntu运行器、Node版本、npm版本和浏览器依赖需要在首次CI运行实际验证；远程动作存在不代表本游戏工作流已经跑通。失败时保存真实日志并修复，不把结构校验写成云端执行通过。

### 35.4 部署完成不等于验收完成

Pages返回URL后，由test:live对该URL进行代表交互、资源与存档检查；默认HTTPS，验证当前buildId与预期提交。部署成功但线上黑屏、资源404、旧缓存、缺字或存档损坏，发布状态为失败。

线上检查失败后按第37章恢复，标记该版本不能交付；不能仅因Actions部署job为绿就通知用户“游戏可用”。

## 36　上线前后必须执行的验收矩阵

### 36.1 本地、CI与线上三层

| 检查 | 本地产物 | CI | 已部署站点 |
| --- | --- | --- | --- |
| 源码、锁文件与构建身份 | 干净重建 | 固定提交与工具版本 | manifest及运行buildId一致 |
| 根路径与子路径 | 两种基址 | /sanguo3/与资源报告 | 真实站点基址 |
| UI与玩法 | 全量独立对照 | 固定环境回归与门禁 | 代表路径与关键画面 |
| 开局到战后恢复 | 完整纵向路径 | 可复现自动化 | 真实URL上执行 |
| 存档 | 异常、冲突、迁移和等价 | 独立测试档 | 同一来源刷新和重开 |
| 浏览器 | 固定主浏览器 | 固定版本 | 兼容清单支持项 |
| 资源与声音 | 缺失、延迟、解码失败 | 请求失败即失败 | HTTPS、缓存、首次音频交互 |
| 回滚 | 旧包与兼容表演练 | 保留前一产物 | 来源不变、恢复可用 |

线上代表路径不替代本地／CI全量对照。生产测试使用专用测试槽位，不覆盖玩家档；自动化创建的数据与正式玩家数据隔离，结束时仅清理自己创建的数据。

### 36.2 建议的产品运行预算

首阶段在固定基准机和主浏览器记录启动耗时、首包大小、资源解码、输入到画面的延迟、帧耗时、内存与存档大小。以实际目标设备测得的可玩基线冻结预算，不把开发机流畅推定为全设备达标。

诊断门槛可先采用60Hz显示下约16.7毫秒的单帧预算目标，随后按目标版本逻辑时序和实测设备调整；这是网页工程目标，不是对原版帧率的断言。超预算先定位纹理、绘制或AI阻塞，不修改规则节奏和随机顺序换性能。

明确支持的桌面浏览器和输入设备，手机、手柄、超高DPR等只有测试后才声明支持。没有完整触屏设计与验收时不能宣称“所有手机可玩”。

### 36.3 内容与资源完整性

逐剧本检查实体总量、人物归属、城市关系、地图连通、全部消息字形和资源引用。发布包中所有正式资源有来源与可分发范围；缺字、占位、未确认数据或未核对规则仍阻断完整复刻发布。

浏览器拒绝音频、存储或全屏权限时给出画布外的明确提示与可恢复路径，规则状态不因浏览器能力变化而悄悄改变。没有网络的情况下是否可继续，按实际缓存策略报告，不默认宣称离线可用。

## 37　更新、缓存、存档与回滚运行手册

### 37.1 首版缓存策略

首版不默认增加Service Worker，减少新旧程序混用的复杂度。静态资源采用内容哈希文件名，清单记录完整版本；入口HTML和release-manifest的更新行为在实际托管环境测试，不假定平台支持自定义缓存头。

后续如增加离线缓存，必须新增下载完整性、旧缓存、更新中断、标签页版本冲突与旧档兼容测试。不能因首次加载慢就临时接入未验收缓存插件。

### 37.2 存档与站点来源

同源下更新代码通常保留IndexedDB，但更换域名、协议或端口会改变来源。发布前记录正式来源，切换前提供可带走的导出和新站导入；不能许诺自动读取另一个来源的本地档。

游戏恢复需要schemaVersion、rulesVersion、dataVersion、assetsVersion与构建兼容表。允许只更换不影响规则的资源时仍校验引用；规则变更不能靠升一个结构版本自动解释旧档。

### 37.3 发布失败的操作顺序

1. 保存失败URL、buildId、时间、请求错误、浏览器日志与可复现路径。
2. 停止将该版本标为可用，保留上一版完整产物与清单。
3. 检查新档能否被上一版读取；有不兼容时采用已验证备份恢复或前向修复，不盲目降代码。
4. 重新部署选定的完整旧产物或修复产物，不混用某些旧脚本和新地图。
5. 在相同正式来源上复测版本、入口、闭环与专用测试槽位，确认恢复后再更新状态。

### 37.4 可观测性与用户反馈

在经典画布之外提供可复制的版本、浏览器、存档格式与错误摘要。默认不上传玩家存档、隐私或全量操作；需要反馈时由用户导出最小复现资料。异常信息能定位资源、命令与阶段，不吞掉错误继续写档。

每次发布至少保留commit、buildId、静态产物摘要、测试报告、兼容表和恢复记录。Git源码回退不等于站点产物回退，也不等于玩家存档回退，三者分别验证。

## 38　最终交付契约与首次上线顺序

### 38.1 交付必须同时包含

完整源码、实际可用的npm命令、运行时版本、锁文件、原版规格与证据索引、可分发资源、全量台账、真实测试结果、已验证dist、发布清单、Actions配置、站点设置说明、正式来源、线上复测与回滚记录。

缺少必要原版参考时不得宣称完全还原；缺少实际应用时不得宣称可运行；仅有构建时不得宣称已部署；仅有URL时不得宣称线上玩法通过。本版补全项目书和辅助工具，未执行游戏开发或站点发布。

门禁分期：exact-release只要求发布前的实施任务完成，不要求RELEASE-EXACT、OPS-LIVE、FINAL-DELIVERY先done；RELEASE-EXACT在真实发布前检查完成后登记结果。部署和线上复测成功后登记OPS-LIVE，delivered要求这些阶段完成，但不要求正在执行的FINAL-DELIVERY先完成自身。最终汇总在delivered成功后登记，避免循环依赖。

### 38.2 首次上线执行清单

资料关口及原版规格完成 → ENG-001真实安装启动 → 纵向闭环可重复 → 全量UI与玩法完成 → 严格复刻门禁通过 → 干净重建与根／子路径测试通过 → 配置Pages与CI → 同一dist部署 → HTTPS代表路径及恢复通过 → 归档与发布报告。

开发AI应连续执行以上流程，修复内部问题，保存交接而不中途改目标。涉及仓库设置、缺失资料或不可用权限时提出具体需求，继续不依赖该前提的任务；不把“需要用户设置Pages”误说成游戏已经上线。

### 38.3 提交给用户的完成报告

写明具体站点与buildId、对应commit、UI与玩法通过范围、原版随机和隐藏机制的证明层次、实际测试计数、支持设备、存档兼容、已知差异和回滚入口。任何未证实项目都原样列出，不被一条“全部完成”覆盖。

文档的作用是让开发步骤、证据和发布结果可检查。能否达到完全一致，最终由已填齐的原版事实与实际运行对照决定；不能由本书页数或AI承诺决定。
